| Stop protecting | `MainWindowViewModel.SaveConfigurationCoreAsync` prompts `ConfirmPurge` for removed selections and sends `PurgeRemovedSelections=true`. | Saving deselection stops future capture and retains history. It neither deletes history nor asks for deletion confirmation. |

### Explicit state and UI

Use `FluxVaultIpcRequest.SetProtectionPaused(bool isPaused)` with a nullable wire field so an omitted desired state is distinguishable from Resume. Keep numeric wire identities, including retired values, unchanged. An unreceipted legacy request without a desired state must be refused clearly; an existing legacy receipt remains queryable/replayable without flipping again. The catalogue hashes the entire serialised request: preserve legacy fingerprints for every affected historical request, including combined save/purge, not only pause. Update all shipping callers and serialization tests together; new fields must not silently alter an old request's canonical representation.

Pause means **no new captures, including manual backup**, matching today's `IsEnabled` contract. History browsing and permitted recovery remain available. The service serialises pause behind accepted capture work; show **Pausing** until that work has safely finished and the state commit is acknowledged. Queued backup checks the newly committed state before source inspection. Do not promise instantaneous cancellation or undo a completed version. Resume restores eligibility; it does not itself run a backup. Before NEXT-005, explicitly show that automatic capture remains unavailable.

Each accepted desired-state operation changes only `IsEnabled`, advances the configuration revision once and atomically completes its receipt, even if already in that state. Exact replay returns that receipt without a new revision or state transition. Fix `MainWindowViewModel.SendBoundAsync` to recognise its revision increment. Pause/Resume retain independent dirty selection edits; later saves must use an explicitly reconciled baseline and preserve the accepted enabled state. A concurrent unconfirmed save or deletion blocks conflicting mutation; its original operation is checked first. A lost acknowledgement shows **Outcome uncertain**, not the requested state as fact.

Use clearly named **Pause protection**, **Resume protection**, **Stop protecting — keep history**, and **Delete history…** actions. Removing scopes through the existing selection editor takes effect only on acknowledged Save. Explain that retained history still follows the existing retention policy; stopping does not create an indefinite archive or change that policy. Re-protection uses the existing selection flow and lineage. Preserve history discovery/recovery for removed scopes.

### Separate deletion contract

Add `PreviewHistoryDeletion` and `DeleteHistory` after the current assigned IPC values; do not repurpose retired commands. Preview is read-only, requires history/maintenance/deletion authority, and returns the server-normalised scope, complete affected version/reference counts, warnings and a bound plan fingerprint. The fingerprint binds VaultId, configuration revision and the exact candidate/dependency set, not just a path/count. Page details using existing browse limits; refuse an incomplete/unbounded preview instead of implying that displayed rows are the whole deletion.

Execution requires `Maintain | DeleteHistory`, OperationId, expected vault revision and the reviewed fingerprint. Recompute the plan under the existing repository lease and refuse if selection, references or candidate contents changed. Derive preserved scopes from the accepted server configuration, never client declarations. Refuse deletion intersecting currently protected history or a required retained reference; show the reason. The existing `ExpandPurgeReferences` can include dependent versions outside the selected path: dependency discovery is not permission to delete them. Refuse such expansion, including unprotected outside-scope dependent versions, and prove they remain recoverable. Reuse the existing manifest/reference validation, metadata deletion and chunk-reference counting. Never delete source files, unrelated versions or a chunk needed by retained history. This slice does not add arbitrary deletion of versions from an actively protected scope.

The confirmation states the scope, counts and irreversibility. Cancellation before admission has no effects. Interruptions after admission retain the operation identity and an uncertain/partial result, including warnings; reconcile before any new destructive request. Do not automatically re-execute an unknown purge. Old save-with-purge receipts remain resolvable, but refuse new combined save-and-delete requests: this intentional contract change prevents an older client bypassing separation. Retain the legacy uncertainty tests; add the new rejection and standalone command tests.

## Risks, deployment and rollback

The material risks are stale commands reversing intent, hidden data deletion, legacy unknown receipt replay, preserved-reference loss and UI acknowledgement races. The contracts and acceptance cases above are the controls. No new service, persistence engine, multi-vault lifecycle or generic command framework is justified.

Ship NEXT-004 separately. After explicit resume, prepare a uniquely versioned candidate with source commit, MSI identity, manifest and hashes; retain it outside the worktree. Reuse the existing `build-candidate.ps1` and reviewed update procedure, adapting their fixed candidate bindings rather than running an old fixed-target script unchanged. Preserve 1.0.7 as the immediate rollback candidate. Review actual MSI tables, process ownership, configuration compatibility, protected bootstrap/ACL/authentication and a checked executable rollback before deployment. Do not choose a release number until the installed state is rechecked.

The old procedure currently rolls 1.0.7 back to 1.0.6; it is evidence and reusable machinery, **not** the rollback target for this new slice. The new procedure must restore the pre-slice accepted 1.0.7 payload/configuration and service policy without dropping history, databases, receipts or binding. No destructive schema change is expected; prove old-binary reads of additive data in an owned fixture. Never restore an older database snapshot over newer accepted history. A software rollback cannot undo an intentionally confirmed history deletion.

Before updating, obtain independent technical acceptance of the concrete candidate and preservation/rollback checks. After updating only FluxVault, verify exact installed payload and repeat the changed real workflow on uniquely owned synthetic folders; preserve all existing source/recovery data. Normal PostgreSQL must never restart. No deletion of valued history is authorised by a generic validation step. Reconcile uncertain installer completion before rollback or corrective redeployment. The user's post-resume standing approval covers these in-scope rollouts without repeated rollout questions.

Completion requires implemented, installed and live-validated capability, applicable gates satisfied, blocking findings closed, documentation accurate and all temporary actors exited. Planning completion does not change NEXT-004's implementation status.
